## 1. 3分で伝えるシステム説明（プレゼン用）

1. **課題**: オリーブ農家は樹木の体調を「目視」に頼っており、主観的で手間がかかる。
   「気づいたときには遅い」リスクがある。
2. **解決**: 撮影した**画像・動画**からオリーブの**葉と果実**を自動で検出し、
   **0〜1の健康スコア**に数値化。**4段階のキャラクター表情**と**日ごとの平均スコアの推移グラフ**で、
   体調の「いま」と「変化」を誰でも見えるようにした。
3. **仕組み**: アップロード → 解析（olive-p を再利用）→ スコア算出 → 判定（しきい値は変更可）→
   キャラクター／グラフで表示。解析はバックグラウンドキューで同時に処理。
4. **堅牢性**: パスワード・セッションの暗号化、ログイン試行制限、自動バックアップと破損復元、
   永不停止設計、プロセス二重化。エラーは機械判別できるコードで統一。
5. **成果の確認方法**: 実際に動画をアップロードし、解析 → 判定 → 表示まで一連で実演可能。

## 2. デモシナリオ（実演の段取り）

| 手順 | 操作 | 見せどころ |
|------|------|-----------|
| 1 | `./start.sh`（または `start.bat`）で起動 | 前提ツール不足でも自動導入して起動する |
| 2 | `curl http://127.0.0.1:8000/api/health` | DB状態・件数・冗長・バックアップ状態を一覧表示 |
| 3 | ダッシュボードで動画をアップロード →解析実行 | キュー処理（TaskBar 進捗）→ 日本語レポート → 注釈画像 |
| 4 | `/olive` を開く | キャラクター表情・スコア・状態別統計・アドバイス |
| 5 | `/tracking` を開く | 1日平均の推移グラフ（ホバーで日付・件数）と CSV/JSON エクスポート |
| 6 | `/admin` でしきい値を変更 | 変更が判定結果に即反映されることを提示 |
| 7 | `/farm-map` | 樹木ごとの体調を色分けで地図表示 |
| 8 | 管理画面「土壌センサー」でテスト通知 | アプリ内＋Webhook/LINE への通知到達を確認 |

所要目安: デモ10分＋質疑20分。

## 3. 想定質問と回答（QA）

### Q1. 健康スコアは何を根拠にどう計算しているのか
解析エンジン olive-p が葉・果実の色・形・しわ・反りを数値化し、0〜1 の
`overall_health_score` として出力します。土壌水分センサーを接続している場合は
見た目と土壌の統合スコア（`combined_health_score`）を優先します
（優先順位は [system-overview.md §3-3](system-overview.md#3-3-土壌水分データとの統合任意)）。

### Q2. 現在の体調判定が「全観測の集計」なのはなぜか
1枚の写真や1フレームは撮影条件の影響を受けやすく、それだけでは判断が安定しません。
そこで、メディア単位で最新の観測を1つ採用し、**最近の観測ほど重みが大きい**
重み付き平均（7日で半減）でスコア化しています。古い情報も捨てず、全期間が数値に反映されます。

### Q3. しきい値の根拠は？
体調判定のしきい値（happy ≥0.75 / good ≥0.55 / caution ≥0.35）は初期値であり、
**管理画面から変更可能**です。農園ごとの基準に合わせられるよう設定として分離しています
（`backend/config/settings.json` の `health_thresholds`）。

### Q4. 観測が1日で何十件もあるとグラフは大丈夫か
グラフは**1日1点＝その日の平均スコア**に集約しているため、件数が多くても折れ線が
絡まりません。ホバーでその日の「N件の平均」を確認でき、実測の最新値はサマリーに別途表示します。

### Q5. データが消えたり壊れたりしないか
- SQLite をWALモードで運用し、30分ごとに一貫性のあるオンラインバックアップ
  （世代ローテーション）を保存。
- 起動時にDB破損を検出した場合は**最新バックアップから自動復元**。
- 手動の一括バックアップ `ops/backup.py` も併用可能（整合性検証オプション付き）。

### Q6. セキュリティはどうなっているか
- パスワードは Argon2id（or PBKDF2）でハッシュ保存。
- セッショントークンは SHA-256 でハッシュ化してDB保存（漏えい時も即利用不可）。
- ログイン試行は IP＋ユーザー単位でロック（15分間5回失敗で15分ロック）。
- ロール（farmer / admin）によるアクセス制御。

### Q7. バックエンドが落ちたらどうなるか
- watchdog が自動再起動（指数バックオフ＋クラッシュループ検知）。
- active/standby の2プロセス構成では、active障害を検知して後継を起動。
- 解析キューは永不停止ループで、一時障害では degraded 起動し自動復旧します。

### Q8. 解析エンジンを自作しているか
解析アルゴリズム本体（検出・スコア算出）は同じ研究室の検出エンジン
[olive-p](https://github.com/UKK-KOSEN/olive-p) をそのまま使用しています。
olive-msystem の開発範囲は、**収集・キュー・保存・判定・可視化・通知・運用のWeb基盤**です。

### Q9. 日本語レポートはどうやって出しているのか
olive-p の英語レポートを `backend/app/translate_report.py` のテンプレート翻訳規則で
全文日本語化します（未知の行は原文のまま残す安全設計）。詳細は
[translation.md](translation.md) を参照。

### Q10. どこまでが「実測」でどこからが「加工」か
- 実測: 各観測のスコア・状態・画像（`observations` にそのまま保存）。
- 加工: 「現在の体調」（重み付き平均）・「1日平均の推移グラフ」（日次要約）・アドバイス。
加工対象と結果はUI上で明示されています（例: グラフの「この日 N 件の平均です」）。

## 5. 非機能要件と評価

| 項目 | 要件 | 実装・測定 |
|------|------|-----------|
| 可用性 | 単一障害で全体停止しない | degraded起動＋自動復旧、watchdog、active/standby、DB自動復元 |
| 性能 | 巨大動画でもメモリを一括消費しない | チャンク書込、最大2GB/ファイル、解析はキューで直列化 |
| 保守性 | 設定変更が即反映・コードとドキュメントが対応 | `settings.json` 動的読込、Documentation Index 対応表 |
| セキュリティ | 資格情報の保護 | Argon2id/PBKDF2、SHA-256セッション、レート制限 |
| データ保全 | 破損耐性・復元性 | WAL、オンラインバックアップ、起動時自動復元 |
| 同時利用 | 複数ユーザー | SQLite `busy_timeout`、農家単位のデータ分離、キュー並列 `WORKERS` |

## 6. 既知の制約と将来拡張

**制約（正直な言及）**
- 冗長構成はプロセス障害向け（ホスト・ディスク障害には非対応）。
- 体調判定は視覚情報（＋任意で土壌水分）ベース。病害の潜在リスク・収量予測は対象外。
- 推移グラフの1日平均は観測データの要約（実測の最新値はサマリーに併記）。
- 監視・冗長化の一部スクリプトは Windows 専用（`ops/redundant-*`, `ops/monitor.ps1`）。

**将来拡張（提案）**
- SQLite → 外部DB（PostgreSQL 等）＋共有ストレージによる**ホスト冗長化**。
- 病害リスク判定・収量予測・灌水レコメンドの追加。
- 画像系モデルの再学習による検出精度向上（olive-p 側の更新に追従）。
- 監視・フェイルオーバー機構のマルチプラットフォーム化。
