# システム仕様書（システム全体像）

この文書は、olive-msystem が「画像・動画からオリーブの体調をどう数値化・見える化しているか」を
コードを読まなくても理解できるように、**仕組みの全体像**を順を追って説明します。

- 対象読者: 審査員・レビュー担当者・新規参画の開発者
- 関連: [README](../README.md)（導入） / [architecture.md](architecture.md)（モジュール・インフラ詳細） / [api.md](api.md)（API） / [operations.md](operations.md)（運用） / [review.md](review.md)（審査用資料：デモシナリオ・想定QA・対応マップ）

---

## 1. このシステムが解決する問題

オリーブ農家にとって、樹木の「いまの体調」を**客観的に**把握することは難しい。

- 目視は主観的で、人によって判断がぶれる。
- 樹木が多く、毎日すべてを確認するのは負荷が大きい。
- 「何かおかしい」と気づいたときには既に重症化していることが多い。

olive-msystem は、スマホやカメラで撮った**画像・動画**を解析して、
オリーブの体調を **0〜1 の健康スコア**に数値化し、
**4段階のキャラクター表情 + 折れ線グラフ**で継続的に見える化します。

```
「目の前のオリーブ、いま大丈夫？」
        ↓ 撮影 ⇨ アップロード（1操作）
「健康スコア 0.82（健康）・前回より +0.05・7日連続で維持」
        ↓ 日々の積み重ね
「推移グラフで、何月頃からじわじわ低下していたか」が一目でわかる
```

## 3. 解析の仕組み（撮る → 解析する）

### 3-1. 入力（画像 / 動画）

| 入力 | 方法 | 解析の単位 |
|------|------|-----------|
| 画像 | `/images` から単発アップロード | その1枚をそのまま解析 |
| 動画 | `/` から複数同時アップロード | 指定時刻の**フレームだけ**を抽出して解析（1動画で複数時刻可） |

動画で観察したい時刻は 3 通りの指定ができます。

- 秒指定: `90`
- 時:分:秒指定: `00:01:30`
- CSVで複数指定: `0,5,10`（動画1本から複数回の「観測」が得られる）

解析は**キュー（Runner）**が受け持ちます。
アップロードは即座に完了し、解析は `WORKERS`（既定2）個のバックグラウンドワーカーが
順次実行します。フロントは `TaskBar` で進捗を表示します。

### 3-2. olive-p（検出エンジン）の処理

解析本体は外部プロジェクト [olive-p](https://github.com/UKK-KOSEN/olive-p) の
`Analyzer` / `VideoProcessor` をそのまま使用します（`backend/app/analyzer.py` がラップ）。

1. **前処理** — 明るさ・コントラスト補正、ぼやけ軽減。
   動画ではまず `realesr-animevideov3`（Real-ESRGAN系）で**4倍アップスケール**し、
   小さな撮影画像でも精度を保ちます。
2. **葉の検出** — 緑の色相・彩度から葉領域を特定し、面積・形状を計測。
3. **果実の検出** — 成熟オリーブの色（黄緑・紫・黒）と円形度から果実を検出。
4. **特徴の分析** — 色・形・しわ・反りを数値化（しわ果の個数もカウント）。
5. **健康スコア算出** — 0〜1 の `overall_health_score` を出力。
6. **レポート生成** — 英語の解析レポートを生成。

`backend/app/translate_report.py` が、この英語レポートを**日本語訳**して保存します
（セクション見出し・検出個体数・信頼度・警告などテンプレート規則で約30種を翻訳。
未知の行は原文のまま残すため、olive-p の仕様変更に強い）。

### 3-3. 土壌水分データとの統合（任意）

土壌水分センサー（外部API）から取得した水分値がある場合、解析結果は
`combined_health_score`（「見た目のストレス」×「土壌の状態」の統合スコア）を優先して使用します。
水分データがない場合は `overall_health_score` をそのまま使用します。

> スコアの優先順位: `combined_health_score` ＞ `overall_health_score` ＞
> `analysis_details.stress.overall_health_score`（`backend/app/health.py`）

## 4. 体調判定の仕組み（数値 → 状態）

### 4-1. 単一観測の状態（`health_state`）

1回の観測（1枚の画像/1フレーム）のスコアは、**編集可能なしきい値**で4段階に分類します。

| スコア範囲 | 状態 (label) | 日本語 | 色 | キャラクター印象 |
|-----------|-------------|--------|-----|------------------|
| `>= 0.75` | happy  | 健康 | 緑 `#4ade80` | にこにこ |
| `>= 0.55` | good   | 良好 | 黄緑 `#a3e635` | ほのぼの |
| `>= 0.35` | caution| 注意 | 黄 `#facc15`   | 心配している |
| それ以外 | danger | 要管理 | 赤 `#f87171`   | ぐったり |

しきい値（0.75 / 0.55 / 0.35）は管理画面から変更可能で、
`backend/config/settings.json` の `health_thresholds` に保存されます。

### 4-2. 現在の体調（`aggregate_health_state`）

「いまのオリーブの体調」は、1回の観測ではなく**これまでの観測すべて**から判定します。
偏りや一瞬の撮影条件に左右されにくくするためです。

**ステップ1 メディア単位で最新1観測を採用**
同一動画・同一画像からの複数観測は、最新（idが最大）の1つだけを候補にします。

**ステップ2 最近の観測を重視した重み付き平均**
日数を重みに変換（`2^(-日数/7)`、**7日ごとに半分にする半減則**）し、
重み付き平均を現在スコアとします。古い観測ほど影響が薄まる一方、全期間の観測が数値に入ります。

**ステップ3 傾向（trend）の判定**
時系列を前半・後半の2グループに分け、後半平均 − 前半平均をとります。
- `+0.03` 以上 → `up`（改善傾向）
- `-0.03` 以下 → `down`（悪化傾向）
- それ以外 → `flat`

**ステップ4 おすすめ（advice）の自動生成**
状態・傾向・水分ストレス（最新3観測の最大値）・しわ果数から、
「水やり・日陰・通風の確認」など具体的な次の行動を生成します。

判定結果は `/api/olive/status` が返し、フロントの `/olive` ページやダッシュボードに使われます。

## 5. キャラクター表示（見える化）

判定状態は、**オリーブのキャラクター画像の表情**で表現します。

| 状態 | 画像アセット |
|------|-------------|
| happy   | `frontend/public/characters/happy.png` |
| good    | `frontend/public/characters/good.png` |
| caution | `frontend/public/characters/caution.png` |
| danger  | `frontend/public/characters/danger.png` |

- 画像は `public/` 配下の静的アセットで、`<img src="/characters/<状態>.png">` で表示。
- 表示箇所: ダッシュボードの「現在の体調」カード、`/olive` のメインカード・状態統計パネル。
- 状態ラベルと画像ファイル名の対応は `backend/app/health.py` の `HEALTH_LABELS` が管理し、
  `/api/olive/status` の `labels` でフロントへも共有されます。

状態名・日本語名・色・画像は1つの定義（`HEALTH_LABELS`）に集約されているため、
表示の揺れが発生しません。

## 6. 体調推移グラフ（継続的な見える化）

`/tracking`・ダッシュボード・`/admin` に表示される `TrendChart`（`frontend/components/charts.tsx`）は、
外部チャートライブラリに依存しない**自作SVG**です。

- **1日1点**: 同一日に複数観測があっても、**その日の平均スコア**を1点とします。
  日に数十件観測してもグラフが「ぐちゃぐちゃ」になりません。
- **普通の折れ線**: 集約した1日1点を直線でそのまま連結します。平均などの特殊な補間は行いません。
- **集約ルール**: 点の位置（x座標）はその日の最終観測時刻、y座標は当日の平均スコア。
  点の色・状態ラベルは平均スコアから判定します。
- **ホバー**: 日付・平均スコア・状態に加え「この日 N 件の平均です」を表示。
- **サマリー**: 最新スコア（実測の最新観測）・前回からの変化・「観測 全N件（1日平均・M日分）」。
- **凡例・集計**: 状態別の件数・比率、ドット数が120点を超えた場合はドットを省略して線のみ表示。

このグラフにより、「いつ頃から低下が始まったか」を一目で読み取れます。

**集計の扱いについて**
- 「1日」は**ブラウザのローカル日付**（端末のタイムゾーン）で区切ります。
  南国や夜間に撮影した観測でも、利用者の体感どおりの「日付」で集計されます。
- 集計に使うのは解析済みの観測スコアのみで、元データ（`observations`）は変更しません。
- 実測の最新観測値はサマリーへそのまま表示し、「加工した数値（日平均）」と「実測値」を
  混同しないよう表示を分けています。

## 7. データの流れ（DBの視点）

```
アップロード
  │  videos / images テーブル（メタ情報 + ファイルは backend/uploads/）
  ▼
解析（Runner → olive-p）
  │  observations テーブル 1行 = 1観測
  │  ・score / health_state.label / result(JSON) / observed_at
  │  ・注釈入り画像は backend/storage/<id>/
  ▼
集計
  │  aggregate_health_state(全観測) ⇨ 現在の体調・傾向・アドバイス
  ▼
表示
  /olive（体調 + キャラクター）/ /tracking（履歴 + グラフ + CSV/JSONエクスポート）
  /calendar（日別の状態）/ /farm-map（樹木ごとに色分け）
```

| テーブル | 役割 |
|----------|------|
| `users` / `sessions` | ユーザー（farmer / admin）とセッショントークン（SHA-256 ハッシュ保存） |
| `videos` / `images` | アップロード資産のメタ情報 |
| `observations` | 解析結果（スコア・状態・結果JSON・注釈画像パス・観測日時） |
| `trees` | 農園マップ用の樹木台帳（農家ごとに一意） |
| `notifications` | アプリ内通知 |
| `sensor_alert_state` / `sensor_alert_events` | センサー異常監視の状態と送信履歴 |

観測日時（`observed_at`）は `backend/app/captured.py` により
写真の撮影時刻メタデータから抽出し、ない場合はアップロード時刻を補います
（「その頃の体調」を正確に残すため）。

## 8. 仕組みを支える品質・運用機能

審査員視点で「すぐ壊れない・止まらない・安全」であることを裏付ける機能です
（詳細は [architecture.md](architecture.md)・[operations.md](operations.md)）。

| カテゴリ | 仕組み |
|----------|--------|
| セキュリティ | Argon2id（or PBKDF2）パスワードハッシュ、Bearerセッショントークン（SHA-256化）、ログイン試行制限、ロール別アクセス制御 |
| 永不停止 | degraded 起動＋自動復旧、解析キュー永不停止ループ、フレーム単位の失敗分離、アップロードのチャンク書込、SQLite `busy_timeout` |
| エラー設計 | 全APIに機械判別可能なエラーコード（`AUTH_*` / `VALIDATION_*` 等）。フロントは再試行も冪等なGET系のみに限定 |
| 冗長化 | active/standby 2プロセス構成（書き込み拒否・ヘルスチェック・フェイルオーバー）。SQLiteはWAL |
| データ保全 | 30分ごとのオンラインバックアップ（世代ローテーション）、起動時のDB破損を検出したら最新バックアップへ自動復元。手動バックアップ `ops/backup.py` 併用可 |
| 異常監視 | 土壌水分センサーの停止・異常・APIエラーを検知し、アプリ内通知＋Webhook/LINEへ段階リマインド・復旧通知 |
| 運用監視 | watchdog（二重起動防止・指数バックオフ・クラッシュループ検知）、`/api/health` 死活監視 |

## 9. 実証・動作確認のしかた（審査時にどう見せるか）

1. **起動**: `start.bat`（Windows）または `./start.sh`（Linux）。前提ツール不足時は自動インストール。
2. **ヘルス確認**:
   ```
   curl http://127.0.0.1:8000/api/health          # DB状態・件数・冗長状態
   curl http://127.0.0.1:8000/api/health/ready    # active かつ DB利用可能で 200
   ```
3. **解析の実演**: ダッシュボードで動画をアップロード → 実行が押せるところを
   見せ、`TaskBar` の進捗 → 解析結果（日本語レポート）→ 注釈画像まで一通りの導線を提示。
4. **体調の見える化**: `/olive` でキャラクター・スコア・状態別統計、
   `/tracking` で1日平均の推移グラフとホバー表示。
5. **管理機能**: `/admin` で農家管理・しきい値変更（変更が判定に即反映される）・
   土壌センサー監視設定の確認。
6. **検証コマンド**: [README の検証コマンド](../README.md#検証コマンド) と
   [operations.md](operations.md) のトラブルシューティングも参照。

## 10. 既知の制約（正直な言及）

- 冗長構成は**プロセス障害**向けです。ホスト・ディスク障害には対応しません（SQLite・ファイルが同一ホストのため）。真正のホスト冗長化には外部DB＋共有ストレージが必要です。
- 体調判定は**視覚情報（＋任意で土壌水分）ベース**です。病害の潜在リスクや収量予測などは対象外としています。
- グラフの1日平均は**観測データの要約**であって実測値そのものではないため、実測の最新値はサマリーに別途表示しています。
